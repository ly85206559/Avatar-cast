# AvatarCast：数字人视频流水线，可复用、可检查

> GitHub 仓库显示名：`Avatar-cast`（公开）；本地目录与包名仍为 `avatarcast`，不跟改。Avatar + Cast：数字人出镜、开口说话、成片播出——名字一眼就是数字人视频，不是只讲嘴型的工具。
>
> AvatarCast 是 **Python 流水线内核 + 轻量 Agent Skill**：可以直接用命令行，也可以让支持 Skill 的助手代为操作。真实生成由外部服务完成，使用者需要自己的服务账号和可用额度。
>
> 两条路线各有用途：**原生视音频**由模型同时生成画面和声音，适合快速试片；**音频驱动**先确定录音，再用录音驱动口型，适合必须保留指定音轨的场景。原生路线不能承诺复用已锁定的 WAV。
>
> 许可证：MIT，见 `LICENSE`。贡献先看 `CONTRIBUTING.md`，第一条是标签纪律：代理分数不许说成真分数，演示占位不许说成唇形证据。

## 快速上手（5 分钟，不花钱）

```bash
pip install -e ".[test]"   # 需要系统里有 ffmpeg / ffprobe
python -m pytest -q
dhp examples/demo-script.json        # 只校验契约、打印缓存键
dhp demo --out outputs/demo          # 离线演示：合成色块 + 正弦音组装出片 + qa.json
```

`dhp demo` 全程离线，实际支出为零，使用色块和正弦音占位，跑通报价门 → 组件过滤 → ffmpeg 组装 → SRT → qa.json。每段都是 `warn`，唇形、人脸、ASR 标为 `not_evaluated`；它验证的是流程，并非真实数字人效果。

## 真实短片：Grok Bot 原生视音频

适合希望先用一张授权形象和一段台词尝试短口播的人。Grok Bot 会调用其可用的视频生成工具，画面与语音同时生成；实际对白和口型仍需要检查，尤其是专名、数字和低置信识别结果。

准备：Python 3.10+、可运行的 FFmpeg、自己的 Grok Bot 账号和可用额度、自己的或已获授权的形象图片及台词。原生短片入口不要求 ffprobe；下面的离线多段演练仍需要 ffprobe。Windows 用户可以使用下面的脚本尝试导入本机 Grok Bot 网关配置。网关使用第三方私有接口，可能随 Grok Bot 版本或远程电脑状态变化，尚未验证所有账号和平台。

网关配置文件包含明文令牌，应限制为本机当前用户读取，不要共享该文件。

Windows 上，在 Grok Bot 桌面应用登录，并先唤醒其远程电脑。然后从项目根目录运行（需要 PowerShell 7，也就是 `pwsh`）：

```powershell
python -m pip install -e ".[native]"
pwsh -NoProfile -File scripts/setup_grok_bot_windows.ps1
dhp native bots
```

`.[native]` 包含备用 FFmpeg；如需多段烧录字幕，还需要带 `subtitles` 滤镜和 `libx264` 编码器的 FFmpeg，以及可用的中文字体。脚本读取已登录的本机应用数据，为当前用户写入 `~/.gbm/config.json`；远程电脑未运行时先唤醒，再重新运行脚本。连接可能失效，可重新导入。其他平台需要自行提供可工作的网关配置；也可通过 `--gateway-config` 指定配置路径。`dhp native bots` 显示可用 Bot 的 ID，复制其中一个作为下面的 `BOT_ID`；它只查询，不生成视频。

先检查当前账号的订阅、额度、是否启用超额或额外付费，以及本次可能费用，再预览计划：

```powershell
dhp native start --image path/to/presenter.png --text "你好，这是数字人口播测试。" --agent-id BOT_ID --output-dir outputs/first-clip --duration 10 --billing allowance
```

不带 `--confirm` 只展示计划，不上传素材或提交生成。检查形象、台词、时长和费用条件后，在同一命令末尾加 `--confirm` 才使用账号现有订阅或额度发起一次请求；若供应商要求额外按次付费，先停止并确认。`allowance` 是用户对使用范围的确认，**不能保证供应商不会计费**；具体额度消耗或金额未知时应记录为未知，而不是零。

请求提交后会在输出目录保存 `job.json`；服务接受请求不等于视频已经生成。默认最多等待 120 秒。如果仍在处理中，或等待、下载中断，可使用已有输出目录继续查询和下载，避免重发生成请求：

```powershell
dhp native resume --output-dir outputs/first-clip
```

`resume` 默认查询一次；需要等待时可加 `--wait-seconds 60`。未完成时命令返回非零状态码，继续用同一目录查询，不要重新提交。完成后，`original.mp4` 是保留原生音轨的原片，`qa.json` 是机器检查报告。报告中的解码和非静音检查不能证明逐字准确、人物一致性或口型同步，这些仍需人工检查。

恢复查询使用最近的对话记录。如果太晚首次查询、原始请求已被大量新消息挤出，可能无法自动关联结果；此时请在 Grok Bot 中查看原任务，不要直接重发生成。

看过和听过后可记录结果：

```powershell
dhp native review --output-dir outputs/first-clip --decision accept --note "画面和声音已人工检查"
```

有至少两个已完成的原生片段时，可在本机拼接（示例中的目录需替换成自己的任务目录）：

```powershell
dhp native assemble --job-dir outputs/first-clip --job-dir outputs/second-clip --output-dir outputs/assembled
```

拼接产出 `final.mp4`、`original.mp4`、`subtitles.srt` 和 `qa.json`。成片会烧录“AI 数字人演绎”画面标识，发布描述栏仍需人工添加标识。字幕按段长和文字估算，并非逐字语音对齐；须人工核对台词、字幕时间和画面，再判断口型、人物及声音跨段一致性。视频会重新编码原生音轨。跨任务自动缓存、锁定音轨和精确口型评分仍未实现。原生 CLI 已在一个账号上完成一次约 10 秒真实生成、下载和用户验收；其他账号和多次独立生成的稳定性仍未验证。把同一条样片重复三次仅能验证本地拼接，不代表三条独立生成的效果通过。

## 给其他人使用

1. 获取这个仓库，在自己的电脑安装 Python，然后在仓库目录执行 `python -m pip install -e ".[native]"`。无需自行部署 GPU 模型；多段烧字幕或离线演练还需满足各自的 FFmpeg / ffprobe 要求。
2. 想先看流程，可使用下面的离线演练，实际不调用生成供应商。想生成真实短片，准备自己的 Grok Bot 账号、额度及可工作的网关配置；用户需要承担自己账号实际产生的费用。
3. 命令行使用者运行上面的 `dhp native` 命令。使用支持 Agent Skills 的助手时，将 `skills/avatarcast` 放到其技能目录，并在助手中打开本仓库；助手根据 Skill 调用同一套 Python 工具。Skill 本身不是视频生成服务，也不会替用户提供订阅或网关。

例如，为当前 Windows 用户安装 Codex Skill（在仓库根目录的 PowerShell 执行；如果目标已存在，先自行检查）：

```powershell
$codexSkills = if ($env:CODEX_HOME) { Join-Path $env:CODEX_HOME 'skills' } else { Join-Path $env:USERPROFILE '.codex/skills' }
New-Item -ItemType Directory -Force -Path $codexSkills | Out-Null
if (Test-Path (Join-Path $codexSkills 'avatarcast')) { throw 'avatarcast skill 已存在，请先检查目标目录' }
Copy-Item -Recurse -Path 'skills/avatarcast' -Destination (Join-Path $codexSkills 'avatarcast')
```

重新打开 Codex 或开始新会话后，在已打开的仓库中让助手使用 `avatarcast` Skill。更新项目后，需要同步更新已复制的 Skill；Python 内核仍来自本地仓库。

项目代码采用 MIT 许可证；第三方服务的账号、支持范围、素材处理和计费按相应服务的当次条款执行。

下面是完整设计思路，读完快速上手再往下看。
>
> 它不是对某一个开源 skill 的复刻。参考的只是通用方法论：用 JSON 做环节间契约、用分段生成拼长视频、用自动指标代替人工看帧。组件参数、提示词模板、包装规则请用你自己的实测数据重新量，不要直接搬运别人的。

## 离线多段流程演练

需要 Python 3.10+、FFmpeg 和 ffprobe。安装项目后，从仓库根目录运行：

```powershell
python -m pip install -e .
python -m dhp.cli examples/demo-script.json --brief examples/demo-brief.json --dry-run --output-dir outputs/dry-run --cache-dir outputs/dry-run-cache
```

演练要求至少两段，`brief.duration_target_sec` 为 30–60 秒。输出目录必须不存在或为空，且与缓存目录相互独立；其中会生成 `final.mp4`、独立的 `subtitles.srt` 和 `qa.json`。再次运行时使用新的空输出目录和同一缓存目录，即可检查并复用有效缓存。修改文本长度会改变按文本长度分配的各段时长，因此可能使其他段的缓存也失效。

该模式完全离线，使用 640×360 分段测试卡与合成音调，不是真实语音或数字人；字幕按模拟段落时长生成，保留独立 SRT，同时烧录到视频内，直接播放即可看到。需要 FFmpeg 含 drawtext/subtitles 滤镜，以及本机安装中文字体。报告中的评分和价格均为模拟值，`quality_verdict` 为 `unverified`，实际支出为零。模拟质检失败最多重试三次，策略名称仅作记录，每次仍生成同类测试卡；FFmpeg 或文件错误会直接停止。它只验证流程与文件产出，不能证明真实唇音、人脸一致性或真实 TTS 质量。面向 Codex 的轻量入口见 [`skills/avatarcast/SKILL.md`](skills/avatarcast/SKILL.md)。

音频驱动路线仍是独立单段入口，需准备授权形象、锁定音频、供应商可访问的素材 URL、API Key 和针对该请求核实的实时价格，并在提交付费请求前获得明确授权；详见 [`docs/API_LIPSYNC.md`](docs/API_LIPSYNC.md)。

以下章节包含项目的目标设计；路线图中的未完成项、重型评分和多段闭环不因上述单段验证而自动完成。

## 0. 先定 6 条设计原则（所有优化都从这里推导）

1. **明确音频来源**：音频驱动路线先锁定音频再生成画面；原生视音频路线同时生成画面和声音，并记录其来源。两种路线使用不同的缓存输入和验收条件。
2. **契约优先（Contract-first）**：每个环节只认 JSON，不认口头约定。环节可替换，契约不许偷偷改。
3. **模型可替换（Provider-agnostic）**：任何一个生成器、TTS、抠像、评分器，都只是实现某个接口。换供应商 = 换配置，不是重写流水线。
4. **质量可检查（Measurable）**：记录实际可测的音画、转写、成本及人工结果；未测量的指标明确标记，低置信专名交人工复核。
5. **产物可追踪（Traceable）**：记录脚本、主播、模型及参数；能安全复用的已完成产物命中缓存。生成模型本身可能非确定性，重生成不保证画面相同。
6. **合规先行（Consent-first）**：只用本人或已授权的声音和形象；成片必须带 AI 演绎标识；不做名人克隆、不做变声冒充。

## 1. 这个项目要解决的六个问题

AvatarCast 不是从某个现成工具改出来的，它从第一行起就是为下面六个问题设计的：

| 问题 | 后果 | 本项目的解法 |
|---|---|---|
| 生成器单一，失败靠人工看帧重拍 | 成本不可控、长视频越长越容易翻车 | 多模型路由 + 自动评分 + 自动重拍闭环（见 §3、§5） |
| 声音是每段单独生成、事后修频谱 | 语调、情绪、停顿锁不住，越长越漂 | 先锁定 TTS 音轨，再音频驱动唇形（见 §4） |
| 质检只看回听准确率和人工抽帧 | 唇音、人脸漂移、烧字幕都靠眼睛 | 五维自动评分器 + 阈值门（见 §5） |
| 剪辑靠人工排固定组件 | 换题材就要重新排，无法从数据学习 | 内容理解自动抽实体/数字/主张 + 数据回流选包装（见 §6） |
| 只能离线成片 | 接不了直播、弹幕、打断、卖货 | 同一套 persona + 时间轴，接实时链路（见 §7，三期） |
| 工程化薄：无缓存、无队列、无跨平台抠像 | 长视频一断就要重跑，换机器就翻车 | 任务化 + 缓存 + Docker + 跨平台抠像（见 §8） |

## 2. 总体架构

```
稿子 / 主播 / 风格
        │
        ▼
┌─────────────────┐     ┌──────────────────┐     ┌──────────────────┐
│  1. 剧本层       │────▶│  2. 音频层（先行） │────▶│  3. 画面层       │
│ brief/script    │     │ TTS + 情绪 + 韵律 │     │ 多模型路由生成    │
└─────────────────┘     └──────────────────┘     └──────────────────┘
        │                        │                        │
        ▼                        ▼                        ▼
┌─────────────────┐     ┌──────────────────┐     ┌──────────────────┐
│  4. 对齐层       │────▶│  5. 质检层（自动） │───▶│  6. 剪辑层       │
│ 逐字时间轴 tl   │     │ 五维评分 + 重拍   │     │ 模板 + 自动包装   │
└─────────────────┘     └──────────────────┘     └──────────────────┘
                                                        │
                                                        ▼
                                              ┌──────────────────┐
                                              │  7. 分发层        │
                                              │ 导出 / 字幕 / 封面 │
                                              └──────────────────┘
```

上图描述音频驱动路线：**剧本 → 锁定音频 → 画面 → 对齐 → 质检 → 剪辑**。原生视音频路线从剧本和形象直接生成画面与声音，再检查和剪辑；它不保证复用指定音轨。

### 模块划分（对应 `src/dhp/`，以代码为准）

- `cache.py`：缓存键（脚本 + 主播 + 模型 + 参数 + 音频哈希）
- `providers.py`：生成器、TTS、唇形、抠像、ASR、评分的统一接口
- `lipsync_api.py`：API 唇形（默认路线，含不自动重试、不猜价格两条硬规则）
- `lipsync_local.py`：本地唇形扩展点（未实现，显式报错）
- `qa.py`：五维评分阈值与 verdict（SyncNet / 人脸 embedding 等重型评分器尚未接入，见 §5）
- `pipeline.py`（v0.2 新增）：报价门、重拍策略、任务计划
- `components.py`（v0.2 新增）：声明式包装组件与校验
- `render.py`（v0.2 新增）：ffmpeg 组装（响度归一、帧率/采样率统一、SRT 导出）
- `cli.py`：`dhp` 命令行（校验、报价、计划、组装；`dhp demo` 为离线演示）
- `demo.py`（v0.4 新增）：离线演示循环，合成占位视频 + qa.json（全段 `warn`，唇形/人脸/ASR 标 `not_evaluated`），零成本、不花钱
- `registry.py`：唇形 provider 注册与默认路由
- 直播链路（ASR → LLM → 流式 TTS → 实时唇形 → RTMP）是三期目标，v0.2 不含

## 3. 多模型路由：不要把所有镜头押在一个模型上

### 3.1 路由表（先按镜头类型分，再按成本分级）

| 镜头类型 | 首选路线 | 兜底路线 | 备注 |
|---|---|---|---|
| 主播特写口播 | 音频驱动唇形模型 | 通用图生视频 + 提示词重拍 | 唇音是硬指标，不达标不许放行 |
| B-roll / 空镜 / 转场 | 通用视频模型（Kling / Wan 类） | 静态图 + 运镜（Ken Burns / 缓推） | 便宜、稳定，优先用 |
| 演示 / 录屏 / 界面 | 真实录屏 + 标注 | 模型生成示意画面（必须标注“示意”） | 别让模型编造界面细节 |
| 场景图 / 封面 | 图像模型 | 模板化封面 | 场景图只做背景，不做口播主体 |

### 3.2 每次生成都要先过“报价门”

生成前必须输出一张成本单，人工或策略确认后才花钱：

```
段数 × 单段秒数 × 模型单价 + 场景图/封面费用
= 预估总价，附：当前余额 / 预算上限 / 命中缓存可省多少
```

策略建议：

- 先拍第 1 段，QA 过线再批量；不要一次把 30 段全押上。
- 每段带 `idempotency_key`（= 输入哈希），重复提交直接返回已有结果。
- 重拍策略的规划顺序：同模型换提示词 → 换同类模型 → 降分辨率/降时长 → 人工介入；真正重拍前需要确认该次消费。提交结果不明时先查询或恢复已有任务，不得盲目重发。
- 分辨率分级：口播主体 720p 起，B-roll 可 480p；不要全片一刀切最高清。

### 3.3 缓存键（这是省钱的核心）

```
cache_key = sha256(脚本段文本 + persona_id + 模型名 + 模型版本
                    + 关键参数 + 参考图哈希 + 音频哈希)
```

有效命中生成缓存可复用已有产物。输入指纹应包含生成路线、稿子、参考图、模型和关键参数；音频驱动路线还包含输入音频哈希，原生路线则记录输出音轨哈希。提交状态不明的任务先恢复，不能假定缓存命中或再次生成安全。

## 4. 音频优先：把声音从“事后修”变成“事前定”

### 4.1 音轨生成的顺序

1. **定音色**：persona 里只存音色 ID / 参考音频哈希，不存“大概像谁”这种模糊描述。
2. **定情绪**：每句标情绪 + 强度 + 语速 + 停顿（见 `schemas/script.json` 的 `emotion` 字段）。情绪是结构化参数，不是提示词里的一句形容词。
3. **生成 + 试听**：先出音频，人工或自动抽查念对率、数字/电话/多音字、繁简体、方言项；不过线先修音频，不许先生成画面再回头改声音。
4. **锁定**：音频一旦锁定，哈希进 task；画面层只读这个哈希。

### 4.2 TTS 选型：不要在没跑盲测前就写死

把 TTS 做成可插拔接口，盲测（同一中性句 × 多种情绪 × 多家模型）跑完再定默认项。选型表只记录可验证的维度：

- 音色一致性（跨段说话人 embedding 漂移）
- 情绪可辨度（盲听至少 4/5 种情绪能分清）
- 中文专项：数字、电话、多音字、繁简体、方言/粤语
- 成本：按中文字符/字节实测换算，不要直接抄英文定价
- 许可证：商用前必须核对权重与 API 条款，见 `docs/COMPLIANCE.md`

### 4.3 唇形：按音频来源选择路线

普通的无声人物动画加后配旁白无法证明唇形同步。原生视音频模型可在同一次生成中产生对白和画面，实际同步仍须检查。本项目的要求：

- 口播主体必须用音频驱动模型（输入 = 参考图 + 已锁定音频），或走带原生唇形的口播服务；
- 唇音分数（SyncNet 类）不过阈值，整段打回重拍，不许靠剪辑遮过去；
- 中文普通话的唇形必须用中文音频实测判，不要用英文 demo 当证据。

### 4.4 声音统一：只做“同一音轨内的统一”，不做“跨音色的伪装”

- 响度归一到 -16 LUFS，采样率统一 48k，段尾保留到说完后 0.25 秒；
- 去齿音、频谱匹配、同一混响，只用于消除“同一个人、不同段录出来像两个人”的接缝；
- 渲染时人声只铺一条，画面轨静音，避免两路差几毫秒造成的梳状滤波。

## 5. 自动质检：五维评分器 + 阈值门（本项目最值得做的部分）

### 5.1 五个维度，一个总分

| 维度 | 测什么 | 工具思路 | 默认阈值（先定，后用数据调） |
|---|---|---|---|
| 念对率 | 画面声音和稿子差几个字 | ASR 转写 vs 稿子算 WER / 准确率 | 准确率 ≥ 85% 才放行，低于则警告或重拍 |
| 唇音同步 | 嘴型和声音对不对得上 | SyncNet 类唇音同步分 | 低于阈值直接重拍，不许人工“看着还行”放行 |
| 人脸一致性 | 跨段是不是同一个人、有没有换脸漂移 | 人脸 embedding 跨段余弦相似度 | 低于阈值重拍该段，并检查参考图是否被污染 |
| 烧字幕 | 模型有没有自己把字幕烧进画面 | OCR 扫描画面下半区 / 全帧 | 检出烧字幕即重拍，不许后期盖字幕遮 |
| 音色漂移 | 跨段音色、情绪有没有跑偏 | 说话人 embedding 漂移 + 情绪分类一致性 | 超阈值先查 TTS 参数，再查音频是否被换过 |

### 5.2 质检报告就是交付物的一部分

每条成片附一份 `qa.json`，至少包含：每段五维分数、是否重拍、重拍次数、重拍原因、总成本、缓存命中率。没有 `qa.json` 的成片，默认视为“未质检”，不许对外宣称“已验证”。

### 5.3 Benchmark：拿同一段稿子跑赢旧路线

做一个固定测试集（同一份 30 秒稿子 + 同一个主播 + 同一套阈值），每次改模型或改策略都跑一遍，对比四个数：

- 重拍率（越低越好）
- 唇音分 / 人脸一致性（越高越好）
- 每分钟成本（越低越好）
- 首次通过率（不重拍就过线的段占比）

只有这四个数同时向好，才算“优化”，单看一个数变好不算。

## 6. 剪辑层：从“人工排组件”到“内容理解 + 数据回流”

### 6.1 包装组件做成声明式，不做硬编码时间线

AvatarCast 的组件是自己的一套：组件只声明“在哪个词上、放什么、放多久”，渲染器负责落位，时间永远来自逐字时间轴，不许写死秒数：

```json
{"use": "PriceTag", "at": "seg:1:不到十块钱", "props": {"value": 9.9}}
```

本仓库自带的组件（见 `src/dhp/components.py`）：`PriceTag`（价格/数字）、`FactCard`（主张 + 证据）、`MapRoute`（地名/路线）、`QuoteCard`（引用）。

- `at` 永远指向时间轴里的逐字位置，不许写死秒数；
- 每个组件都要有“无数据时不渲染”的兜底：没数字就不上数字卡片，别编一个数字填上去；
- 未知组件名、缺 `at`、缺必填 `props`，校验直接报错，不许静默跳过。

### 6.2 自动抽取：让稿子自己长出包装

- 数字 / 价格 / 百分比 → 自动生成计数器、对比条；
- 地名 / 路线 → 自动生成地图路线（离线地图数据，不许模型编造地名）；
- 主张 / 结论 → 自动配证据卡（证据必须来自稿子或引用源，不许模型现编）；
- 人物 / 机构 → 自动配标注卡（姓名、身份必须来自稿子）。

抽取错了宁可不上，也不上错的。抽取结果进 `edit.json`，人工可改，改完要留痕。

### 6.3 数据回流（只做可验证的闭环）

- 发布后回流完播率、3 秒留存、跳出点（按段聚合，不做单用户画像）；
- 哪种开场、哪种节奏留存高，就调高它在路由里的权重；调权重要有版本号和前后对比，不要悄悄改；
- 回流只影响“包装选择”，不影响“事实内容”：留存高不等于可以编造数字。

### 6.4 渲染与导出

- 渲染器与组件分离：同一份 `tl.json + edit.json`，可以出 16:9、9:16、1:1 三种尺寸；
- 导出清单：成片 + SRT 字幕 + 封面图 + 标题 A/B 候选 + QA 报告；
- 景深字（文字在人身后）要做跨平台抠像（RMBG / BiRefNet 类），不要只依赖某一家操作系统的独占 API；中景才做，人占画面过大时降级为普通花字，并写进 QA 报告。

## 7. 三期路线图（每期都能单独交付、单独验证）

### 一期：换掉生成和质检（核心，必做）

目标：同一段稿子，成本降 30% 以上；重拍不需要人工看帧。

- [x] v0.2 已做：报价门 + 缓存 + 重拍策略（`pipeline.py`）、声明式组件（`components.py`）、ffmpeg 组装（`render.py`）、Benchmark（`scripts/benchmark.py`）
- [x] v0.3 已做：Vosk 中文 ASR 实测接入、TTS 命令缝、唇音启发式（非 SyncNet）、画面一致性代理（非人脸 embedding）、本地唇形环境检查、API 真跑脚本（未花钱）、直播状态机（接口）
- [x] v0.4 已做：MIT 许可证、CONTRIBUTING、CI、pyproject 依赖分层、README 快速上手、离线演示命令（零成本、占位视频、qa.json 全段 `warn`）、固定测试集基线落盘（`benchmark/baseline-v0.3.json`）
- [ ] 保留 JSON 契约，生成层换成多模型适配器（接口已定，适配器待接）
- [ ] 接入音频优先流程：TTS 锁定 → 音频驱动唇形 → 对齐（API 唇形已实现提交规则，尚未真跑）
- [ ] 五维自动评分器 + 阈值门 + 自动重拍（阈值已定，重型评分模型未接入）
- [ ] Benchmark 测试集 + `qa.json` 交付（对比工具已做，固定测试集待跑）
- 验收：固定 30 秒稿子，重拍率、唇音分、每分钟成本三项同时优于“单模型 + 人工看帧”的基线

### 二期：锁定声音和情绪（差异化，值得做）

目标：同一个主播，能“开心 / 严肃 / 促销”切换情绪，且音色不漂。

- [ ] 盲测胜出的 TTS 接入为默认音频层，情绪/语速/停顿结构化
- [ ] 情绪一致性进 QA（跨段情绪分类不许跳变）
- [ ] 多主播、多语言（先做中文 + 粤语，再扩其他语言）
- 验收：盲听 5 种情绪至少 4 种可辨，且跨段音色漂移在阈值内

### 三期：直播和分发（从工具升到“数字人员工”）

目标：同一套 persona，能接实时互动，而不只是离线成片。

- [ ] ASR → LLM → 流式 TTS → 实时唇形 → RTMP
- [ ] 打断、弹幕、商品卡片、话术兜底（答不上来先承认，不要编造）
- [ ] 一键多尺寸导出、SRT、封面 A/B、完播回流
- 验收：端到端延迟、打断成功率、直播中断恢复时间三项有实测数，不写“大概很快”

## 8. 工程化：长视频不出错、可复用

- **任务化**：每段是一个独立任务，可重跑、可断点续跑；整片失败不许从头重跑。
- **队列**：本地先用 SQLite + 文件队列起步，量上来了再换 Temporal / Celery；不要一开始就上重型中间件。
- **Docker**：ffmpeg、Python、Node、模型依赖全部进镜像；`docker compose up` 能跑通一期最小闭环。
- **可观测**：每段留日志：模型、参数、耗时、成本、QA 分数、重拍原因；成本账本按日汇总。
- **测试**：契约校验测试、缓存命中测试、QA 阈值测试、成本单测试；没有测试的改动不许合入。
- **版本**：persona、模型、组件、路由策略全部带版本号；成片元数据里写清这四个版本，出问题能回溯。

## 9. 成本与风险（先说清楚，再动手）

- 成本大头在口播生成，不在剪辑。省钱的顺序：缓存命中 > B-roll 降分辨率 > 路由降级 > 砍时长。
- 风险最高的不是模型，是“以为验证过了，其实没验证”：唇音、许可证、中文效果、价格，四项没实测就不许写进 README 的“已验证”一节。
- 模型价格、许可证、权重可下载性，变化很快。本仓库只记录“核查日期 + 来源 + 当时口径”，不承诺长期有效；动手前按 `docs/COMPLIANCE.md` 的清单再核一次。

## 10. 从哪里开始（给今天的你）

1. 先把 `schemas/` 里的契约定下来，跑通 `tests/test_contracts.py`；
2. 再做一期最小闭环：1 段稿子 → TTS 锁定 → 音频驱动唇形（先走 API）→ 五维评分 → 出片 + `qa.json`；
3. 用固定 30 秒测试集跑 Benchmark，记下基线数，再谈“优化了多少”；
4. 盲测结果出来后，再把二期的情绪层接进来，不要提前写死 TTS 选型。
